OpenShell uses drivers to connect the gateway to workload runtimes and
credential stores. Drivers implement a stable capability boundary while the
gateway owns the public API, authorization, workspace scoping, and resource
lifecycle.

## Compute Drivers

Compute drivers create, inspect, and delete sandbox workloads. OpenShell ships
drivers for Kubernetes, Docker, Podman, virtual machines, and Windows MXC. An
external compute driver communicates with the gateway over a Unix domain
socket and negotiates its protocol version and capabilities before serving
requests.

For built-in driver configuration and behavior, refer to
[Runtimes](/how-it-works/sandboxes/runtimes). For implementation details, refer
to each driver crate:

### Using an External Compute Driver

External compute drivers must implement [`compute_driver.proto`](https://github.com/NVIDIA/OpenShell/blob/main/proto/compute_driver.proto).
Refer to [Protocol Negotiation](/extensibility/overview#protocol-negotiation) for the metadata and capability requirements, and
[Isolation Backends](/extensibility/isolation-backends) for the workload runtime
contract. Your driver must also acknowledge the gateway's
[resource admission policy](/how-it-works/gateways/configuration#external-resource-admission).

Run your driver as a separate service listening on a Unix domain socket. The
gateway does not start or supervise it. Restrict socket access to the gateway
user and make the socket accessible from the gateway's host or container.

Select a name that is not reserved by a built-in driver, then add it and the
socket path to your existing `gateway.toml`:

```toml
[openshell]
version = 2

[openshell.gateway]
compute_driver = "example-compute"

[openshell.drivers.example-compute]
socket_path = "/run/openshell/example-compute.sock"
```

Start the driver, then start or restart the gateway with this configuration. Use
`openshell gateway info` from a CLI connected to that gateway to verify the
active driver and negotiated capabilities. See the
[Extension Driver configuration reference](/how-it-works/gateways/configuration#extension-driver)
for configuration details.

### Suspend and Resume

A compute driver that can retain workload state lists
`openshell.compute.suspend-resume` in its supported capabilities and implements
`SuspendSandbox`. The gateway rejects suspend and resume requests for drivers
that do not advertise it. The driver stores the restore reference; the gateway
never receives it. Suspension also requires an isolation backend that advertises
`openshell.sandbox.suspend-resume`. Refer to
[Isolation Backends](/extensibility/isolation-backends#suspend-and-resume).

The driver coordinates retained state with the backend through its native
provisioning or control integration. The shared supervisor launch metadata
contains identity and transport settings; it contains no restore references,
reference-file paths, or restart policy.

To implement `SuspendSandbox`, send `SIGUSR1` to the supervisor and wait,
with a bound, for it to exit with status 0. The supervisor calls
`SuspendBoundary`, and the backend freezes the workload, retains its state,
and fences the generation. The backend must make its retained-state handle
available to the driver through their private integration before confirming
suspension. The supervisor exits without terminating the boundary or reporting
a main-process exit. It ignores `SIGUSR1` when the backend lacks support.

For `StartSandbox` with `resume` set, provision the backend to restore the
retained state under the new launch identity. Pass the request's
`restart_if_restore_fails` choice through the driver-to-backend integration.
The supervisor attaches using `OpenBoundary`; the backend reports `RESTORED`
or an explicitly permitted `COLD_START_FALLBACK`. The backend must reject
missing, invalid, or superseded state instead of silently starting fresh.
Keep the restored workload frozen until the new supervisor admits and starts it.

If you can observe a failed restore before `StartSandbox` returns, keep the
retained-state handle and return an error so the gateway can return the sandbox
to Suspended for another attempt. `StartSandbox` without `resume`,
`StopSandbox`, and `DeleteSandbox` discard retained state.

## Credential Drivers

Credential drivers store provider credentials behind opaque handles. The
gateway resolves those handles when a provider is attached without persisting
the secret value in the provider record. OpenShell includes database,
Kubernetes Secret, and Vault-compatible credential drivers.

Configure the active credential driver in the
[Gateway Configuration](/how-it-works/gateways/configuration#credential-drivers).
For implementation details, refer to each driver crate:

| Driver | Crate |
|---|---|
| Database | [`openshell-driver-db-credstore`](https://github.com/NVIDIA/OpenShell/tree/main/crates/openshell-driver-db-credstore) |
| Kubernetes Secrets | [`openshell-driver-kubernetes-secrets`](https://github.com/NVIDIA/OpenShell/tree/main/crates/openshell-driver-kubernetes-secrets) |
| Vault | [`openshell-driver-vault`](https://github.com/NVIDIA/OpenShell/tree/main/crates/openshell-driver-vault) |

External credential drivers implement [`credential_driver.proto`](https://github.com/NVIDIA/OpenShell/blob/main/proto/credential_driver.proto).

## Compatibility

Drivers exchange peer metadata with the gateway and advertise their extension
family capability. Upgrade both peers together when the protocol version
changes. Refer to [Extension Protocol Negotiation](/extensibility/overview#protocol-negotiation)
for the negotiation contract.
